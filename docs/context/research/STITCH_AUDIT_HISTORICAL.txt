1. THE PRODUCT DIRECTION TO KEEP

Crewmori should feel like a helpful business team for a freelancer: friendly, competent, calm, and easy to return to. It should make the next decision obvious and let the owner inspect the reasoning when useful.

The distinctive visual and emotional direction is already present in the first two approved screens:

A. crewmori_magazine_editorial_warmth_desktop — Home
B. crewmori_team_overview_global_studio — Team overview

These are the primary visual anchors. Later generated screens are useful for discovering possible content and workflows, but should not have equal authority over style, information density, or layout.

Preserve from the anchors:
- Warm ivory/offwhite page and panel surfaces, restrained borders, ample breathing room, rounded cards, and forest-green primary actions.
- Newsreader editorial headings with readable Inter body text; retain utility typography only where it earns its place.
- Soft peach, butter, sage/mint, lilac, and sky accents used consistently for teammate identity and meaningful states.
- The illustrated specialist characters, including Scout with the lens. They are part of the product's identity, not disposable decoration.
- Home as a readable owner briefing: an important decision, a short account of what moved forward, and clear next actions.
- Team as the main visual moment: the muted map, stable teammate positions, visible handoffs, and an owner studio receiving useful outputs.
- Human coworker language: “Found two projects that fit this brief” or “Your offer is ready to review.”

Preserve appearance without preserving mistakes. The approved screens still contain invented or inconsistent sample claims, placeholder interactions, and motion that needs behavioral rules.

2. WHAT WENT WRONG

2.1 The export contains competing design authorities

The two anchors import Newsreader and use an editorial heading system. All 14 subsequent screens omit Newsreader and revert to Manrope headings. The bundled quiet_workbench/DESIGN.md also describes Manrope headings and an older shell, rather than the newly approved editorial identity.

That is a concrete source of drift: a model following the written design file can reasonably produce something different from the approved screenshots. The future pack must replace this ambiguity with one corrected design contract and an explicit precedence order.

Other shell differences in source include sidebars of 212px, 224px, and 256px, and headers of 64px, 68px, and 72px. The approved Home uses warm colors such as #F7F5EE and #FAF8F3 and 24px panel corners; later screens fall back to a different canvas and denser components. These values are evidence to reconcile, not a final token specification.

2.2 Internal detail became the default interface

Later pages repeatedly show agent commentary, capacity diagnostics, financial analysis, trust scores, evidence trails, pipeline health, and several competing action groups at once. This makes the owner interpret the system before doing the task.

The solution is progressive disclosure: keep the task's decision in the main view, expose supporting evidence on request, and put the complete agent execution trail in Team. Complexity may exist in the system without appearing in every screen.

2.3 The product's personality was replaced with generic dashboard conventions

The anchors contain 18 and 14 inline SVG elements respectively, including character and interface artwork. Many later pages use generic Material Symbols or initials instead of the specialist characters. Merely adding cream backgrounds and rounded panels later would not restore the identity; typography, composition, illustration, copy, and density must stay coherent together.

2.4 Screens were generated as separate documents rather than one application

The archive has no shared application shell, router, package manifest, normalized fixtures, or cross-screen state store. A static scan counts 238 button elements and 165 href="#" uses across the 16 HTML files. These are affordances to audit, not proof that every one is broken. There are also 15 external raster-image references, plus CDN Tailwind and externally loaded fonts/icons.

The future frontend needs shared components and a single state model. Copying these files into routes would preserve the inconsistency and misleading interactions.

2.5 More specified content was treated as more visible content

The earlier all-screens scope encouraged elaborate standalone artboards. The new pack needs to distinguish “the implementation must support this” from “show this by default.” A long specification should produce a simpler experience, not a longer page.

3. PRIORITY FIXES

P0 — resolve before the final implementation prompt is sealed:
- Establish one visual authority and retire the conflicting old DESIGN.md as normative guidance.
- Agree the product boundary, route ownership, and actual build scope.
- Define one canonical entity/state model and explicit sample scenarios.
- Separate drafting, approving, sending, buyer acceptance, payment confirmation, and capacity reservation.
- Decide which actions are local simulations and which, if any, use real services.
- Define the complete observable behavior of every visible enabled control.
- Remove unsubstantiated financial guarantees, official verification claims, and unexplained scores.

P1 — encode as mandatory implementation requirements:
- Rebuild later screens with the anchor typography, spacing, palette, mascots, and common shell.
- Reduce default density and move specialist/evidence details into optional panels.
- Provide actual navigation, editable state, validation, saved results, recovery, and working downloads where offered.
- Synchronize the same records across Home, Team, Opportunities, Work, and Money.
- Add keyboard behavior, app-owned dialogs, focus management, contrast, and reduced motion.
- Replace inconsistent hard-coded dates/currencies/totals with derived values.

P2 — polish after the core experience works:
- Refine motion timing, character gestures, handoff choreography, and empty states.
- Tune narrow desktop layouts, typography at different widths, and long-content behavior.
- Add only the secondary views that genuinely help the agreed demo.

5. VISUAL AND DENSITY RULES TO WRITE INTO THE FUTURE PACK

One shared shell: sidebar, header, content grid, account area, tool shortcuts, focus mode, notification access, page gutters, and overlay behavior must be owned by shared components.

One typographic hierarchy: editorial serif titles at a restrained number of levels, readable body text, quiet metadata. Avoid tiny serif text everywhere, oversized all-caps labels, and a new font hierarchy on each route.

One set of spacing, color, radius, border, and elevation tokens: extract and reconcile from the anchors, then map into runtime CSS/theme once. No independent hard-coded page palettes. The old DESIGN.md must be marked superseded and replaced in the final pack, rather than left beside a contradictory new document.

One clear job per view: say what the owner came to decide or do. Establish one dominant action for the current state. Secondary actions remain discoverable but do not compete equally.

Three layers of information:
1. Immediate: decision, next action, essential state, essential amount/date.
2. Supporting: expanded detail or a contextual drawer after the owner asks.
3. Complete trace: Team activity, sources, record/version history, and task inspector.

Soft guidance for a calm first view: a brief introduction, the main task/list, and only a few relevant updates. Do not turn this into a rigid “three cards everywhere” template. Money still needs usable rows; a full form still needs enough space.

Team owns the choreography. Other routes can show a small teammate attribution and an “Inspect” link. They should not all inherit an always-open agent-analysis column.

Copy should describe outcomes in ordinary language. Replace phrases such as “calibrated financial escrow gates,” “capacity defense,” “velocity protection,” and “receiving calibrated handoff” with clear statements about the user's work.

Friendly language is welcome, but precise status wins: “I drafted a follow-up. Review it?” is honest; “Sorted!” is not adequate when a payment is still unmatched.

6. MOTION SHOULD EXPRESS REAL STATE

The wow factor can become dynamic later, provided its behavior is specified now.

Proposed motion vocabulary:
- Idle: subtle breathing/blink/occasional gesture; most of the canvas remains still.
- Working: one restrained activity cue on the actual active teammate/task.
- Handoff: a short path animation between the source and destination for a real event.
- Waiting for owner: a steady badge and clear action, not constant bouncing.
- Complete: one brief confirmation, then settle into a completed state.
- Blocked/disconnected: readable state and recovery action, without decorative panic.

Cursor activity must stay inside its own visualization, never obscure labels, chase the real pointer, move controls, or intercept clicks. It should not suggest a teammate is working when no task exists. Avoid replaying every historic event indefinitely.

Catch me up should produce a bounded recap of actual sample events since the chosen point. Focus mode should have one documented effect across the app. Pause/reduced-motion states must retain all information and actions. Narrow layouts can transform the map into a coherent ordered view; they must not shrink it to unreadable dots.

Exact motion durations, paths, repeat limits, and focus behavior remain to be designed. The next builder should not invent unrelated cursor loops per screen.

9. CANONICAL DATA AND STATE PROBLEMS

The Northstar story is promising because it connects the whole app, but it has drifted across screens.

The source story currently suggests:
- Original request: four assets, $500 budget, five business days.
- Proposed reduced offer: two assets, $450, estimated 12 hours, five business days.
- Proposed deposit: 60% of gross total = $270.
- Approved Team screen's initial state: awaiting owner review; no deposit received; no capacity reserved.

Conflicting evidence:
- Opportunity detail uses nine hours / $50 per hour while Team uses 12 hours and Activity uses an 8.5-hour + 3.5-hour split.
- Team says $450 / 12 hours protects a $75/hour floor. That arithmetic yields $37.50/hour; the floor claim needs correction or a real different definition.
- Home and offer detail sometimes claim locked capacity before approval/reservation.
- Draft invoice and expense content claim receipt of the $270 advance while the anchor offer remains awaiting review.
- FX assumptions differ between 15,000 and 15,536 IDR/USD.
- Client geography/contact details and teammate identity change across files.
- Dates mix 2024, 2025, quarter/week labels, and October 2026.

Some screens could deliberately illustrate later demo stages. That is acceptable only if scenarios explicitly say so and transitions connect them. They cannot all be treated as one default snapshot.

Proposed model principle:
- Stable IDs for owner, client, opportunity, offer, project, task, invoice, payment, expense, connection, artifact, approval, and activity event.
- Shared records; display values derived from them.
- Versioned offers; approval applies to a particular version.
- Stage-specific fixture variants with clear initial conditions.
- Date-only values separate from timestamps; timezone and business calendar explicit.
- Money in integer minor units, with currency and rounding policy.
- Expected payment separate from confirmed transaction; gross, fee, and net separate.
- Buyer-visible projections separate from internal economics, capacity notes, and private sources.
- Sample provider outcomes clearly separated from actual connection/transaction state.

Illustrative arithmetic from the current sample, not a product promise:
At a sample 2% fee and 15,000 IDR/USD:
60% deposit: $270 gross - $5.40 fee = $264.60 net = IDR 3,969,000.
40% deposit: $180 gross - $3.60 fee = $176.40 net = IDR 2,646,000.
Against IDR 3,000,000 cost, the latter is short by IDR 354,000.
After a $270 gross deposit on a $450 invoice, gross balance is $180. Do not subtract net receipt from gross invoice total.

Any fee/FX calculation must state whether it is a sample estimate, when it is assumed, and which cost it includes. Do not invent escrow, guaranteed exchange rates, protected capital, verified identity, or official central-bank rates to make the UI seem capable.

10. USER FLOW SPECIFICATION — REQUIRED FORMAT

The founder specifically wants detailed AI-readable flows. This is essential. A list of pages and a few happy-path arrows is insufficient.

Each flow should include:
flow_id; goal; priority; actor/audience; entry points; owning route; record IDs; fixture variant; preconditions; permissions; initial state; policy/source references; ordered steps; alternate paths; exit/back behavior; persistence; cross-screen effects; success criteria; prohibited side effects; test cases.

Each step should include:
- Stable control ID and exact visible label/location.
- Trigger: pointer, keyboard, route load, task event, or simulated provider callback.
- Relevant state before the action and enabled/disabled conditions.
- Inputs and validation, including where errors appear.
- Pending feedback and duplicate-click behavior.
- Exact mutation: record, old state, new state, affected fields/version.
- Visible result: content, feedback, focus destination, navigation, and scroll behavior.
- Related-record and related-screen updates.
- Failure, timeout, stale-version, disconnected, and retry behavior as applicable.
- Cancel/close behavior and preservation of drafts.
- Refresh, Back/Forward, direct-link, repeated-run, and reset behavior.
- Observable acceptance assertion and things that must not happen.

Keep a control registry linking every visible enabled control to its flow step, and every required flow step to a visible result/test. No decorative working-looking controls with no result. If a capability is out of scope, remove the action or label the limitation honestly.

Core state families to specify once, then reference:
loading; ready; empty; no results; validation error; submitting; success; recoverable failure; disconnected; stale/conflict; cancelled; and permission/unavailable where relevant.

The final flow format may be YAML/JSON plus concise Markdown explanation. It must remain machine-readable and avoid repeating the same policy in contradictory prose files.

The global Ask/Delegate input needs its own contract. For a frontend-only prototype, enumerate supported sample intents, what typed inputs may change, deterministic outcomes, interrupt/cancel behavior, and a useful response for unsupported requests. A text box must not imply unrestricted live AI capability if it only recognizes a few demo requests. Likewise, background activity should come from the shared sample event/task model, rather than random reassuring messages unrelated to records.

11. WORKED FLOW DRAFT — NORTHSTAR OFFER

This is a specification example for discussion, not approval of the proposed business lifecycle.

FLOW: offer.review_approve_send_accept
Actor: freelancer owner, then sample buyer.
Record: offer_northstar_001, version 1.
Initial fixture: awaiting_owner_review; two sample deliverables; currency: USD, amount_minor: 45000 ($450.00); proposed deposit 60%; five business days with countdown trigger still undecided; 12-hour internal estimate; no payment; no reservation.

Entry:
Home Review offer, Team Review offer, and Offers detail all open the same offer ID and version. Return preserves the source context and relevant list state.

Review:
Owner sees the client-visible scope, price, delivery basis, deposit, and message. Internal assessment is optional and clearly owner-only. Source evidence opens without losing the offer.

Edit:
Edit opens the agreed editor with the current version. Cancel restores the unchanged saved version. Save validates scope, amount, deposit, and delivery fields. Invalid inputs remain visible and editable. Successful save creates a new draft version and clears approval for the superseded version. No message is sent.

Approve:
Approval must check the version being reviewed. Success records owner_approved and approved_version. A stale version blocks with a refresh/review option. This step alone does not send terms, record buyer acceptance, collect money, or reserve time under this draft proposal.

Send:
A separate Send offer action previews buyer-safe content and destination. Cancel leaves the approved record unchanged. In sample mode, send updates the canonical record to sent/awaiting_buyer_acceptance and logs a sample message. Duplicate clicks create one message/event. If the necessary connection is unavailable, preserve the draft and offer the agreed recovery or sample-only path. No real email is implied.

Buyer acceptance, if buyer scope is included:
Only the current shared, non-expired offer version can be accepted. Acceptance creates the project once, provisionally in Awaiting deposit, and a request with currency: USD, amount_minor: 27000 ($270.00). The exact creation/reservation rule still needs the founder's decision. Private pricing rationale and studio capacity never appear in buyer content.

Sample payment:
A deliberate demo event changes expected payment to confirmed, records gross 27,000 / fee 540 / net 26,460 USD minor units under the illustrative 2% fixture, and leaves 18,000 gross due. It does not claim to process real funds. Replaying confirmation must not create a second receipt.

After payment:
Project onboarding/start, calendar reservation, and deadline calculation follow the eventual agreed rule about acceptance, deposit, and required client inputs. This rule is unresolved and must not be guessed by the builder.

Cross-screen effects:
Home removes or updates the decision card; Team logs the completed review/send and shows the next actual task; Opportunities shows the current offer version/state; Work shows the accepted project only at the agreed point; Money shows the correct expected/confirmed amounts; Calendar shows only the appropriate proposed/reserved/confirmed commitment. Refresh preserves committed sample state.

Negative assertions:
Opening an offer does not approve it. Approval does not imply buyer acceptance. A sent offer is not a paid invoice. Expected deposit is not received money. Editing does not retain stale approval. Retrying does not duplicate records. Owner-only facts do not leak into buyer projections.

14. HOW TO USE HUNDREDS OF MOBBIN REFERENCES WITHOUT LOSING DIRECTION

Index before synthesis. Assign each image a reference ID, source product, screen/flow type, relevant pattern, and founder preference if known. Preserve original files and filenames in an archive, while creating a concise manifest.

Separate visual identity from interaction inspiration:
- The two Crewmori anchors control the visual identity.
